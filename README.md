# Classroom 11 — как HTTP работает по сети

Это классная работа к занятию «OSI, TCP/UDP, TLS и версии HTTP». Здесь мы не строим новый CRUD: мы по очереди открываем механизмы, которые в прошлом уроке скрывал `net/http`.

## Что увидим руками

| Шаг | Эксперимент | Главный вывод |
|---|---|---|
| 01 | TCP echo | `Accept` создаёт `net.Conn`, а TCP переносит поток байтов без границ сообщений |
| 02 | UDP echo | одна запись создаёт отдельную датаграмму; соединение и `Accept` не нужны |
| 03 | raw HTTP | HTTP/1.1-запрос можно записать обычным текстом в TCP-соединение |
| 04 | `httptrace` | `http.Client` скрывает connect, ожидание первого байта и reuse соединения |
| 05 | TLS + HTTP/2 | TLS защищает байты, ALPN выбирает протокол `h2` |
| 06 | timeout | запрос обязан иметь границу ожидания |

## Быстрый старт

Нужен Go 1.22 или новее.

```bash
make ci
make demos
```

`make demos` запускает все короткие примеры. Для live coding удобнее идти по одному шагу.

## Live coding: рекомендуемый порядок

### 1. TCP: соединение и поток

В первом терминале:

```bash
make tcp-server
```

Во втором:

```bash
make tcp-client
```

Откройте `internal/networklab/tcp.go`. Найдите `Accept`, `ReadString`/`Scanner` и `Write`. Обратите внимание: символ `\n` добавили мы сами. TCP не знает, где заканчивается наше логическое сообщение.

### 2. UDP: отдельные сообщения

```bash
make udp-server
# во втором терминале
make udp-client
```

Сравните `net.Listener.Accept` с `net.PacketConn.ReadFrom`. Для UDP сервер получает адрес вместе с каждой датаграммой.

### 3. HTTP/1.1 без `http.Client`

```bash
make raw-http
```

Пример поднимает локальный handler, соединяется с ним через `net.Dial` и отправляет:

```http
GET /health HTTP/1.1
Host: 127.0.0.1:PORT
Connection: close


```

Специально удалите `Host` или последнюю пустую строку и обсудите, почему HTTP-сервер не может корректно определить конец headers. После эксперимента верните рабочий код.

### 4. Что делает `http.Client`

```bash
make http-trace
```

Ищем две строки `GotConn`. У первого запроса ожидаем `reused=false`, у второго — `reused=true`. Переиспользование возможно потому, что body прочитан до конца и закрыт.

### 5. TLS и HTTP/2

```bash
make tls-http2
```

Пример использует локальный тестовый сертификат и выводит три независимых факта:

- `HTTP/2.0` — версия HTTP;
- `TLS 1.3` — версия защищённого соединения;
- `h2` — результат ALPN: клиент и сервер выбрали HTTP/2.

### 6. Медленный сервер и timeout

```bash
make timeouts
```

Handler отвечает через 150 мс, а клиент ждёт только 40 мс. Ожидаем ошибку с `context deadline exceeded`. Это не «поломка Go»: программа выполнила наше правило не ждать бесконечно.

## Что здесь намеренно упрощено

- Мы используем loopback (`127.0.0.1`), поэтому пакеты не уходят в интернет.
- Мы не пишем собственный TCP/IP stack и не разбираем Ethernet-кадры в Go.
- Локальный TLS-сервер использует сертификат, которому доверяет только созданный для него тестовый client.
- Мы не настраиваем production TLS, reverse proxy или load balancer — это темы следующих занятий.

## Частые ошибки

1. Считать, что один `Write` в TCP равен одному `Read`.
2. Читать TCP «пока не станет пусто» вместо явного framing: `\n`, длины или формата протокола.
3. Ожидать от UDP доставки, порядка и повторной отправки.
4. Забывать `Host` в HTTP/1.1.
5. Забывать пустую строку между headers и body.
6. Создавать новый `http.Client`/`Transport` на каждый запрос.
7. Не читать и не закрывать `response.Body`.
8. Делать сетевой запрос без timeout/context.
9. Отключать проверку сертификата через `InsecureSkipVerify` и считать это исправлением.
10. Путать TCP keepalive с повторным использованием HTTP-соединения.

Подробные антипримеры: [`docs/bad-examples.md`](docs/bad-examples.md).
